Root Component Strategy

How should the weeks view share state with the month view?

A

Nest inside existing Root

<Root><WeeksView.Root>...</WeeksView.Root></Root>

Pros

  • Zero duplication — existing Root unchanged, weeks view just adds a layer
  • Both views can coexist in the same tree (e.g., month picker + weeks view side by side)
  • Smallest API change — existing consumers unaffected

Cons

  • Two nested Roots is confusing — which Root do props go on?
  • Navigation state conflicts — Root tracks "current month" which may not make sense for weeks view
  • WeeksView.Root becomes dependent on parent context existing, can't be used standalone
  • Awkward if someone only wants the weeks view — they still need to wrap in Root
B

Independent Root with duplicated props

<WeeksView.Root value={...} min={...} weekCount={6}>...</WeeksView.Root>

Pros

  • Each view is fully self-contained — use one or the other, no nesting
  • Simple mental model — one Root per view, all props in one place
  • No risk of context conflicts between views

Cons

  • Prop duplication — selection, min/max, locale, disabled dates, callbacks all repeated in both Root types
  • Shared logic must be extracted into hooks anyway (so why not share the provider too?)
  • Using both views together requires syncing state externally
  • Divergence risk — same prop might behave slightly differently across the two Roots over time
C

Shared CalendarProvider extracted from Root

<CalendarProvider value={...} min={...}><WeeksView weekCount={6}>...</WeeksView></CalendarProvider>

Pros

  • Single source of truth for shared state — selection, min/max, locale, disabled dates defined once
  • Each view only adds its own props — clean separation of concerns
  • Both views can coexist and stay in sync automatically (shared context)
  • Forces clean factoring — shared vs view-specific logic is explicit
  • Natural extension point for future views (year view, agenda view, etc.)

Cons

  • Breaking change — existing <Root> API must change or become a convenience wrapper
  • More components to understand — three layers instead of one (Provider → View Root → Components)
  • Over-engineered if only two views will ever exist
  • Requires deciding upfront exactly which state is "shared" vs "view-specific" — get it wrong and you're shuffling props later

Recommendation: C (with a compat wrapper)

Extract shared state into a CalendarProvider, then make the existing Root a thin wrapper that composes CalendarProvider + MonthView.Root — so current consumers see no breaking change. The weeks view gets WeeksView.Root which reads from the same provider. Clean, extensible, backwards-compatible.
