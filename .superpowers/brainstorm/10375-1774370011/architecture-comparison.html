Architecture: Mode on Root vs Separate Component Tree

How should the continuous-weeks view relate to the existing month grid?

A

New mode on existing Root

A view="weeks" prop on Root switches grid rendering

Pros

  • Single entry point — consumers learn one API
  • Shared state is automatic (selection, disabled dates, min/max all just work)
  • Existing components like DayButton, DayCell stay the same
  • Switching between views at runtime is trivial (toggle a prop)

Cons

  • Root's props/state grow — weeks-only props (weekCount, firstWeek, overflow behavior) clutter the API for month-grid users
  • Grid component needs branching logic for two rendering modes
  • New components (month separators, week nav buttons) only make sense in weeks mode — consumers could misuse them in month mode
  • Harder to tree-shake — consumers who only want month-grid still bundle weeks logic
  • Risk of the Root becoming a "god component" as features accumulate
B

Separate compound component tree

New top-level component (e.g. WeeksView.Root) with its own components, sharing context with DatePicker

Pros

  • Clean separation — each view's API only exposes what's relevant
  • No branching in Grid — each view has its own grid component purpose-built for its layout
  • New components (separators, week nav) live naturally under the new namespace
  • Tree-shakeable — don't use it, don't bundle it
  • Easier path to infinite scroll later — the weeks view can evolve independently
  • Shared selection/state still possible via shared context or composition

Cons

  • More API surface to learn — two component trees instead of one
  • Shared logic (day rendering, keyboard nav, selection) needs to be extracted into shared hooks/utils to avoid duplication
  • Runtime view switching requires swapping component trees rather than toggling a prop
  • Risk of the two views drifting apart in behavior if shared logic isn't well-factored

Recommendation: B

The weeks view has fundamentally different layout semantics (continuous rows vs month grids), unique components (separators, week navigation), and a future that diverges further (infinite scroll). Keeping it separate avoids polluting the month-grid API while still sharing core logic through hooks and utilities.
